`com.mysql:mysql-connector-j`

Before making any changes, inspect the repository and identify:

- Maven dependencies and build configuration.
- Existing package structure and architectural conventions.
- MySQL version and connection configuration.
- Persistence framework: Spring Data JPA, Hibernate, JDBC, or another existing approach.

- Existing tests, CI/CD configuration, and deployment setup.
- Any current functionality that must remain unchanged.

Do not assume that the application uses JPA simply because it uses MySQL. Confirm the actual persistence technology.

### Technology decisions

- Backend: existing Java and Spring Boot stack.

- AI: Spring AI with a configurable LLM provider.
- Primary AI provider: OpenAI API, unless the repository or project configuration specifies otherwise.

## 3. Product Requirements

Build an AI-powered polling application where users can create polls, vote, see results, and use AI to generate poll content and understand voting trends.

### 3.1 User and Access Management

Support:
- User registration and authentication, where not already provided.
- User profiles and account status.
- Roles and permissions appropriate to the application.
- Poll ownership and access control.
- Public and private polls.
- Administrative operations with explicit authorization.
- Audit logging for sensitive actions.

Enforce authorization in the backend. Never trust a user ID, role, creator ID, or permission supplied by the client.

### 3.2 Poll Lifecycle

Support:
- Creating and editing draft polls.
- Publishing polls.
- Opening and closing polls.
- Archiving completed polls.
- Configurable start and end times.
- Single-choice and multiple-choice voting.
- Poll categories and tags.
- Search, filtering, and pagination.
- Configurable visibility of results.
- Configurable voting eligibility and vote-changing rules.

Define explicit state transitions, for example:

DRAFT → PUBLISHED → CLOSED → ARCHIVED

Validate every transition in the business layer. Prevent voting before opening, after closing, or when the poll is otherwise ineligible to accept votes.

Define the exact behavior for concurrent poll closure and vote submission, including how deadlines are enforced.

### 3.3 Voting System

Treat voting correctness as a critical business invariant.

Requirements:
- Validate the poll, voter eligibility, poll status, and selected options.
- Prevent duplicate voting according to the poll's voting policy.
- Support single-choice and multiple-choice polls.
- Handle simultaneous requests safely across multiple application instances.
- Support idempotent request retries.
- Prevent double counting.
- Keep vote records and related selections transactionally consistent.
- Return clear and consistent errors for invalid or conflicting submissions.
- Ensure unauthorized users cannot vote in restricted polls.
- Define whether users can change or withdraw their votes.

Do not depend exclusively on an application-level check before insertion to prevent duplicates.

Use MySQL constraints, transactions, appropriate indexes, and a justified concurrency-control strategy.

Test the implementation against real MySQL using multiple database connections. Do not treat an H2-only test as proof of MySQL concurrency correctness.

## 4. AI Features

### 4.1 AI Poll Generator

Allow a user to enter a natural-language request such as:

"Create a poll for software engineers about their preferred AI coding assistants."

Generate structured output containing:
- Poll question.
- Answer options.
- Category and tags.
- Optional description.
- Optional follow-up questions.

Requirements:
- Integrate using Spring AI.
- Use structured output and schema validation.
- Validate generated content on the server.
- Enforce maximum question length, option count, and content size.
- Handle malformed responses and provider failures.
- Apply timeouts, bounded retries, and concurrency limits.
- Require user review before publication.
- Keep AI generation separate from poll persistence and voting logic.
- Do not let AI output bypass business rules or authorization.
- Never blindly retry non-idempotent operations.

### 4.2 AI-Powered Poll Analytics

Allow users to request a plain-language explanation of poll results.

Example:

"Summarize the voting trends and explain which option is most popular."

Implement the workflow as follows:

1. Retrieve authorized poll results.
2. Calculate authoritative counts and percentages using deterministic backend logic or verified SQL aggregates.
3. Prepare a minimal, validated result dataset.
4. Pass the relevant aggregates to the LLM.
5. Generate a concise, evidence-based explanation.
6. Associate the explanation with the relevant poll version or result timestamp.

The LLM must not invent authoritative counts or percentages.

Handle ties, small sample sizes, missing data, and incomplete results appropriately. Clearly distinguish factual observations from interpretations.

Cache summaries only when their cache keys incorporate the relevant poll version, result state, and prompt/model configuration. Invalidate stale results when appropriate.

### 4.3 Natural-Language Poll Search

Support queries such as:

"Find open polls about Java that have more than 100 votes."

Convert natural-language input into a constrained, typed search specification.

Validate filters, pagination, and permissions in the backend. Never execute arbitrary SQL, database commands, or generated code supplied by an LLM.

### 4.4 AI-Assisted Abuse Detection

Optionally identify suspicious voting patterns using deterministic rules and AI-assisted risk analysis.

Start with reliable safeguards:
- Authentication.
- Rate limiting.
- Duplicate-vote prevention.
- Idempotency.
- Eligibility validation.
- Audit events.

Treat AI-generated risk scores as signals requiring evaluation, not proof of fraud. Do not automatically penalize users solely because an LLM labels their behavior suspicious.

## 5. MySQL Database Design

Design a normalized relational schema that integrates with the existing user model.

Candidate tables:
- users, or the existing equivalent.
- polls.
- poll_options.
- votes.
- vote_selections for multiple-choice submissions.
- result_aggregates if justified.
- audit_events where required.
- AI usage metadata where required.

Adapt names, identifiers, types, and relationships to existing project conventions.

### Database requirements

- Use primary keys and foreign keys.
- Add unique constraints for critical business invariants.
- Add indexes based on query patterns.
- Use transactions for multi-table vote submissions.
- Prevent duplicate selections within one vote.
- Ensure selected options belong to the poll being voted on.
- Document transaction boundaries and isolation assumptions.
- Use an explicit UTC timestamp convention.
- Use the existing migration framework or introduce one only when justified.
- Never make destructive schema changes without explicit approval.
- Avoid unbounded collections of votes embedded in a single poll record.

For a single-vote-per-user policy, evaluate a unique constraint on `(poll_id, user_id)` in the vote record.

For multiple-choice polls, model a vote submission and its selected options separately. Prevent duplicate option selections and ensure that all selections belong to the correct poll.

Consider materialized result aggregates only when workload measurements justify them. If aggregates are maintained asynchronously, implement idempotency, reconciliation, and rebuilding procedures.

Keep committed vote records as the authoritative source.

## 6. REST API Design

Define versioned REST APIs using the repository's conventions.

Possible endpoints include:

- POST `/api/v1/polls`
- GET `/api/v1/polls/{pollId}`
- PATCH `/api/v1/polls/{pollId}`
- POST `/api/v1/polls/{pollId}/publish`
- POST `/api/v1/polls/{pollId}/close`
- POST `/api/v1/polls/{pollId}/votes`
- GET `/api/v1/polls/{pollId}/results`
- POST `/api/v1/ai/polls/generate`
- POST `/api/v1/ai/polls/{pollId}/analyze`
- GET `/api/v1/polls/search`

Treat these as starting points and refine them based on the existing application architecture.

For every endpoint, document:
- Request and response schemas.
- Authentication and permissions.
- Input validation.
- Success and failure status codes.
- Idempotency behavior.
- Pagination.
- Rate limits where applicable.

Use appropriate HTTP status codes, including 400, 401, 403, 404, 409, 422 where appropriate, 429, and 503.

Implement centralized exception handling. Never expose stack traces, credentials, raw database exceptions, or internal provider errors to clients.

## 7. Architecture and Code Quality

Prefer a modular monolith unless actual requirements justify distributed services.

Separate responsibilities into cohesive modules or packages, such as:
- identity
- polls
- voting
- results
- AI
- notifications
- audit
- configuration
- common

Apply:
- SOLID principles.
- Dependency inversion.
- Separation of concerns.
- Constructor injection.
- Clear domain boundaries.
- Thin controllers.
- Explicit transaction boundaries.
- Centralized validation and exception handling.
- Immutable DTOs where appropriate.
- Consistent naming and package conventions.

Do not place business logic in controllers or couple domain logic directly to LLM providers.

Use interfaces where they create useful boundaries, not simply to increase the number of classes.

Avoid god classes, unnecessary abstractions, duplicated business logic, premature microservices, and excessive design patterns.

Implement:

- Minimal context and bounded input sizes.
- Structured output with only required fields.
- Configurable model selection.

- Request timeouts.
- Bounded concurrency.
- Rate limiting.

## 10. Concurrency and Distributed-System Reliability

Design for multiple concurrent users and multiple application instances.

Address:
- Simultaneous vote submissions.
- Duplicate client retries.
- Poll closure racing with voting.
- Database connection pool limits.
- Redis failure, if Redis is used.
- LLM provider timeouts and throttling.
- Duplicate event delivery, if messaging is used.
- Graceful shutdown.
- Bounded executors and queues.
- Backpressure.
- Recovery from interrupted processing.

Use timeouts and appropriate isolation or bulkheads around external dependencies.

If asynchronous messaging is introduced, define event schemas, idempotent consumers, retry handling, dead-letter processing, replay procedures, and monitoring.

Evaluate the transactional outbox pattern if reliable event publication following a database transaction is required.

Do not claim exactly-once processing without defining and proving the relevant guarantees. Use durable state and idempotency to protect business outcomes.
